# Eine Events-Tabelle trägt CRM, Stream und Eingriff

Für Aufgabe C reicht eine schlanke Architektur: **SQLite im WAL-Modus mit einer append-only `events`-Tabelle als einziger Quelle der Wahrheit**, die von allen Threads in kurzen `BEGIN IMMEDIATE`-Transaktionen beschrieben wird. Dazu kommt **FastAPIs eingebautes SSE (`fastapi.sse`, ab Version 0.135)**, das diese Tabelle per `id > last_id` mitliest, und **eine einzige statische HTML-Seite** mit genau einer `EventSource`, die Eingriffe als gewöhnliche POST-Requests schickt. Drei technische Fallen entscheiden, ob das am Wochenende stabil läuft. Erstens darf eine Schreibtransaktion nie aus einem Lesezugriff „hochgestuft“ werden, sonst kommt sofort „database is locked“, egal wie hoch der Timeout ist. Zweitens darf eine sqlite3-Verbindung nicht über `yield`-Grenzen eines synchronen Generators hinweg gehalten werden. Drittens darf der Stream-Endpunkt nie mit 4xx/5xx antworten, weil der Browser sich dann endgültig abmeldet. Bei der Human-in-the-Loop-Oberfläche passt die etablierte Intervention aus Agent-Frameworks (Approve, Edit, Reject, Respond, Pause, Übergabe, globaler Not-Aus) zur Challenge, aber nur mit einer Einschränkung: Ein globales „Freigabe vor Versand“ würde die Zeitpunkte zerstören (15 Punkte, voll nur unter 2 Minuten). Deshalb sollte nur bedingt gegatet werden, mit Countdown und automatischem Versand bei Timeout. Weil nur die erste Quote im Thread zählt, braucht „Übernehmen“ außerdem eine atomare Sperre in der Datenbank, nicht nur einen Button.

## WAL, Verbindung pro Thread und BEGIN IMMEDIATE verhindern „database is locked“

Das Fundament ist der WAL-Modus. Dort **blockieren Leser keine Schreiber und Schreiber keine Leser, es gibt aber immer nur einen Schreiber gleichzeitig** ([sqlite.org WAL](https://www.sqlite.org/wal.html)). Für unser Lastprofil (eine RFQ alle 6 Minuten plus Carrier-Bids und Events, also einige Dutzend Schreibvorgänge pro Minute) ist dieser eine Schreiber kein Engpass. Entscheidend ist, welche PRAGMAs wo gelten. `journal_mode=WAL` ist **persistent in der Datei gespeichert** und muss nur einmal gesetzt werden ([sqlite.org WAL](https://www.sqlite.org/wal.html)). `synchronous`, `foreign_keys` und `busy_timeout` gelten dagegen **pro Verbindung** und fallen bei jeder neuen Verbindung auf die Standardwerte zurück. `foreign_keys` ist standardmäßig sogar AUS und wirkt innerhalb einer Transaktion nicht ([sqlite.org PRAGMA](https://www.sqlite.org/pragma.html)). `synchronous=NORMAL` ist laut SQLite „die beste Balance“ für WAL. Der Preis dafür ist, dass die letzten Commits bei einem Stromausfall verloren gehen können ([sqlite.org PRAGMA](https://www.sqlite.org/pragma.html)), was für ein Hackathon-CRM vertretbar ist. Pythons `sqlite3.connect(timeout=…)` setzt intern denselben Busy-Handler, Standard sind 5 Sekunden ([Python sqlite3](https://docs.python.org/3.12/library/sqlite3.html)). Ein Wert von 10 Sekunden gibt bei kurzzeitiger Konkurrenz mehr Luft.

Bei Threads ist die richtige Wahl **eine Verbindung pro Thread über `threading.local`**. Standardmäßig wirft eine Verbindung einen `ProgrammingError`, wenn ein anderer Thread sie benutzt. Mit `check_same_thread=False` müssen Schreibzugriffe laut Doku „vom Nutzer serialisiert werden, um Datenkorruption zu vermeiden“ ([Python sqlite3](https://docs.python.org/3.12/library/sqlite3.html)). Eine geteilte Verbindung hätte zudem einen gemeinsamen Transaktionszustand: Das `BEGIN` eines Threads würde die Statements eines anderen verschlucken. Per-Thread-Verbindungen überlassen das Sperren SQLite selbst und erhalten die Parallelität zwischen Lesern und dem Schreiber.

Die größte Falle ist die Transaktionsart. Im DEFERRED-Modus, also Pythons Standard vor 3.12, beginnt eine Transaktion mit einem SELECT als Lesetransaktion. Ein späteres INSERT versucht dann ein Upgrade und bekommt sonst `SQLITE_BUSY` ([sqlite.org BEGIN](https://www.sqlite.org/lang_transaction.html)). Bert Hubert beschreibt das so: Egal wie hoch der Timeout eingestellt ist, dieses Szenario liefert **„always … an instant SQLITE_BUSY error“**. Seine Konsequenz: Wer weiß, dass er schreiben wird, nimmt `BEGIN IMMEDIATE` ([berthub.eu](https://berthub.eu/articles/posts/a-brief-post-on-sqlite3-database-locked-despite-timeout/)). Simon Willison nennt das SQLites „single biggest footgun“ ([simonwillison.net](https://www.simonwillison.net/2025/Feb/17/sqlite-busy)). Genau dieses Muster kommt bei uns ständig vor, etwa „Session lesen, Status prüfen, Quote schreiben“. Unter Python 3.11 gibt es das `autocommit`-Attribut noch nicht (erst ab 3.12) ([Python sqlite3](https://docs.python.org/3.12/library/sqlite3.html)). Der 3.11-kompatible Weg ist `isolation_level=None` (Python öffnet nie implizit Transaktionen) plus ein eigener `tx()`-Kontextmanager. `with conn:` taugt dafür nicht, denn ohne offene Transaktion tut es laut Doku schlicht nichts ([Python sqlite3](https://docs.python.org/3.12/library/sqlite3.html)).

```python
# db.py – nur stdlib, Python 3.11
import json, sqlite3, threading
from contextlib import contextmanager
from datetime import datetime, timezone

DB_PATH = "crm.db"            # nur lokale Platte
_local = threading.local()

def utcnow():
    return datetime.now(timezone.utc).isoformat(timespec="milliseconds").replace("+00:00", "Z")

def conn():
    c = getattr(_local, "conn", None)
    if c is None:
        c = sqlite3.connect(DB_PATH, timeout=10, isolation_level=None)
        c.row_factory = sqlite3.Row
        for p in ("journal_mode=WAL", "synchronous=NORMAL", "foreign_keys=ON", "busy_timeout=10000"):
            c.execute(f"PRAGMA {p}")
        _local.conn = c
    return c

@contextmanager
def tx():                      # Schreibsperre gleich am Anfang -> kein Upgrade-Fehler
    c = conn(); c.execute("BEGIN IMMEDIATE")
    try:
        yield c
    except BaseException:
        c.execute("ROLLBACK"); raise
    else:
        c.execute("COMMIT")

def q(sql, p=()):  return conn().execute(sql, p).fetchall()   # immer materialisieren
def q1(sql, p=()): return conn().execute(sql, p).fetchone()

def emit(c, session_id, type_, payload=None):   # immer innerhalb von tx() aufrufen
    return c.execute("INSERT INTO events(session_id,type,payload,created_at) VALUES(?,?,?,?)",
                     (session_id, type_, json.dumps(payload or {}), utcnow())).lastrowid

# with db.tx() as c:
#     c.execute("UPDATE sessions SET status='quoted', updated_at=? WHERE id=?", (db.utcnow(), sid))
#     db.emit(c, sid, "quote_sent", {"price": 1234.5, "currency": "EUR", "cost_usd": 0.004})
```

Zwei Betriebsregeln gehören dazu. **Innerhalb von `tx()` passieren nie LLM-, Portal- oder Mail-Aufrufe.** Die langsame Arbeit kommt zuerst, danach wird das Ergebnis in einer Transaktion von Millisekunden geschrieben. Zweitens hält ein nicht ausgelesener Cursor einen Lese-Snapshot offen. Ein dauerhaft aktiver Leser verhindert Checkpoints, sodass **die WAL-Datei unbegrenzt wächst** ([sqlite.org WAL](https://www.sqlite.org/wal.html)). Deshalb liefern `q()`/`q1()` immer fertige Zeilen. Die DB-Datei gehört auf die lokale Platte: **WAL funktioniert nicht über Netzwerkdateisysteme** ([sqlite.org WAL](https://www.sqlite.org/wal.html)), und Netzlaufwerke haben schon Korruption verursacht ([sqlite.org over network](https://www.sqlite.org/useovernet.html)). Ein Cloud-Sync-Ordner oder ein Docker-Mount auf einen Share ist also tabu. Taucht trotzdem „locked“ auf, hilft es, `e.sqlite_errorname` zu loggen: `SQLITE_BUSY_SNAPSHOT` bedeutet ein Upgrade im eigenen Code, ein `SQLITE_BUSY` nach vollem Timeout eine zu lange Transaktion. Eine dedizierte Writer-Queue wäre die Eskalationsstufe, ist bei dieser Last aber unnötig.

## Das Schema macht den Event-Log zum Rückgrat von CRM und Stream

Das Datenmodell sollte drei Aufgaben gleichzeitig erfüllen: CRM-Historie (Quotes, Buchungen, gewonnen/verloren), Tracking-Grundlage für den +10-Bonus und Live-Feed fürs UI. Das gelingt mit **Zustandstabellen** (`sessions`, `mails`, `quotes`, `bookings`, `llm_calls`) **plus einer append-only `events`-Tabelle mit `INTEGER PRIMARY KEY AUTOINCREMENT`**. Deren `id` dient direkt als SSE-Cursor und `Last-Event-ID`. Die zentrale Regel: **Das Event wird in derselben Transaktion geschrieben wie die Zustandsänderung**, also Quote-Insert und `quote_sent`-Event zusammen. So sieht das UI nie einen Zustand ohne Event oder umgekehrt. Events werden nie geändert oder gelöscht.

Für Idempotenz sorgt SQLites UPSERT: `INSERT … ON CONFLICT(col) DO UPDATE SET x=excluded.x` oder `DO NOTHING`. Das Konfliktziel muss ein PRIMARY KEY, eine UNIQUE-Constraint oder ein Unique-Index sein, und UPSERT greift **nicht** bei verletzten NOT-NULL-, CHECK- oder Fremdschlüssel-Constraints ([sqlite.org UPSERT](https://www.sqlite.org/lang_upsert.html)). Daraus folgen die natürlichen Schlüssel: `UNIQUE(message_id)` auf Mails, damit der Poller dieselbe Mail gefahrlos zweimal sehen kann, `UNIQUE(thread_id)` auf Sessions und `UNIQUE(rate_id)` auf Buchungen. Variable Daten wie geparste RFQ-Felder, LLM-Output oder Portal-Payloads passen in JSON-Spalten. JSON-Funktionen sind **seit SQLite 3.38.0 standardmäßig eingebaut**, inklusive der Operatoren `->` und `->>`, und JSON wird als normaler Text gespeichert ([sqlite.org JSON](https://www.sqlite.org/json1.html)). Ein `CHECK (json_valid(data))` schützt vor kaputten Payloads. Felder, nach denen gefiltert oder gejoint wird (Status, thread_id, session_id, Preis, Währung, Kosten), gehören in echte Spalten. Beim Start sollte `sqlite3.sqlite_version` geprüft werden.

Für Zeitstempel empfiehlt sich ISO-8601-UTC als TEXT, in Python erzeugt (`2026-11-21T14:03:05.123Z`). Pythons Standard-Datetime-Adapter sind **ab 3.12 veraltet**, und der Standard-Konverter **ignoriert UTC-Offsets und liefert naive Datetimes** ([Python sqlite3](https://docs.python.org/3.12/library/sqlite3.html)). Strings mit fester Breite sortieren lexikalisch korrekt, `ORDER BY created_at` funktioniert also. `sqlite3.Row` ist ein schneller Row-Factory mit Zugriff per Spaltenname ([Python sqlite3](https://docs.python.org/3.12/library/sqlite3.html)), lässt sich aber nicht als JSON serialisieren: Vor der Rückgabe aus FastAPI wird `dict(row)` angewendet.

Die Recherche-Notizen verwenden zwei verschiedene Status-Sets: `new/pricing/quoted/booked/lost/error/human` im DB-Entwurf und `open/quoted/booked/lost/paused/error` in der UX-Recherche. Ich empfehle, das zu trennen. Der **Geschäftsstatus** (`new`, `pricing`, `quoted`, `booked`, `lost`, `error`) ist eine Spalte. Der **Kontrollmodus** (`auto`, `paused`, `human`) ist eine zweite Spalte. Eine pausierte Session ist nämlich trotzdem „pricing“ oder „quoted“. Mit beiden Dimensionen in einer Spalte verliert man Information und baut Race Conditions. Dieses Event-Schema sollte das Team früh festlegen, weil Personen A und B es befüllen: `{id, session_id, ts, type, status, label, duration_ms, cost_usd, payload}`. Die `cost_usd` pro Event speist direkt die Kostenanzeige pro Quote, die das Dashboard braucht (40 Punkte hängen an den Gateway-Kosten).

## Natives FastAPI-SSE ersetzt sse-starlette und Handarbeit

Seit **FastAPI 0.135.0 gibt es SSE eingebaut**: `from fastapi.sse import EventSourceResponse, ServerSentEvent` und `yield` im Pfad-Handler. Es sendet automatisch **alle 15 Sekunden einen Keep-Alive-Ping** und setzt **`Cache-Control: no-cache` und `X-Accel-Buffering: no`** ([FastAPI SSE Tutorial](https://fastapi.tiangolo.com/tutorial/server-sent-events/)). Normale `def`-Generatoren werden laut Doku so ausgeführt, dass sie den Event-Loop nicht blockieren. Das passt genau zur Vorgabe „Threads statt asyncio“. `ServerSentEvent` kennt `data` (immer JSON-kodiert, ein String bekommt also Anführungszeichen), `raw_data` (unverändert, schließt `data` aus), `event`, `id` (einzeilig, ohne NUL), `retry` und `comment`. Synchrone Iterables laufen im Threadpool ([FastAPI SSE Referenz](https://fastapi.tiangolo.com/reference/sse/)). Damit entfällt die zusätzliche Abhängigkeit sse-starlette. Falls jemand im Team von „sse-starlette 2.x“ ausgeht: Die aktuelle Linie ist 3.x, und sie bleibt nur Fallback für ältere FastAPI-Versionen. Sie bietet `ping`, `send_timeout` und Shutdown-Optionen und warnt, DB-Sessions im Generator statt als Dependency anzulegen ([sse-starlette](https://github.com/sysid/sse-starlette)). Ein handgebautes `StreamingResponse` müsste Pings und Header selbst liefern.

Beim synchronen Generator lauert eine nicht offensichtliche Falle. Starlette führt einen Sync-Iterator schrittweise im Threadpool aus, **jedes `next()` kann also auf einem anderen Worker-Thread laufen**. Eine im Generator einmal geöffnete und über Iterationen weiterverwendete sqlite3-Verbindung scheitert dann an der Thread-Prüfung (`check_same_thread`, [Python sqlite3](https://docs.python.org/3.12/library/sqlite3.html)). Zwei Lösungen sind sauber. Man öffnet pro Poll eine kurzlebige Verbindung, oder man ruft wie oben `db.q()` auf, das bei jedem Aufruf die Verbindung des *aktuellen* Threads aus `threading.local` holt. Wichtig ist nur: **keine Verbindung und keinen Cursor über ein `yield` hinweg halten.** Außerdem läuft ein `finally`-Block in einem Sync-Generator nach einem Client-Disconnect nicht zuverlässig sofort. Ressourcen, die aufgeräumt werden müssen, gehören daher gar nicht erst in den Generator.

Die Threadpool-Rechnung muss man kennen. Starlettes Standard-Threadpool hat **nur 40 Tokens**, geteilt mit allen synchronen `def`-Endpunkten. Erhöhen lässt er sich über `anyio.to_thread.current_default_thread_limiter().total_tokens` ([Starlette Threadpool](https://www.starlette.dev/threadpool)). Ein offener Sync-Stream, der zwischen Polls mit `time.sleep(1)` schläft, belegt fast dauerhaft ein Token. Bei 1 bis 5 Dashboard-Tabs ist das egal. Falls die Demo mit vielen Zuschauer-Tabs läuft, wäre die eine bewusste Ausnahme von „kein asyncio“ ein `async def`-Generator nur für diesen Endpunkt, mit `await anyio.sleep(1)`. Ein leerlaufender Stream belegt dann keinen Thread.

```python
# app.py (Auszug)
from typing import Annotated, Iterable
import time, json
from fastapi import FastAPI, Header
from fastapi.sse import EventSourceResponse, ServerSentEvent
from fastapi.staticfiles import StaticFiles
import db

app = FastAPI()

@app.get("/api/events/stream", response_class=EventSourceResponse)
def events_stream(last_event_id: Annotated[int | None, Header()] = None,
                  since: int = 0) -> Iterable[ServerSentEvent]:
    last = last_event_id if last_event_id is not None else since   # Header gewinnt beim Reconnect
    yield ServerSentEvent(comment="connected", retry=3000)
    while True:
        try:
            rows = db.q("SELECT * FROM events WHERE id>? ORDER BY id LIMIT 200", (last,))
        except Exception:
            rows = []          # loggen, aber nie mit 5xx abbrechen
        for r in rows:
            last = r["id"]
            yield ServerSentEvent(id=str(r["id"]), raw_data=json.dumps(dict(r)))
        if not rows:
            time.sleep(1.0)

# ... POST-Endpunkte für Eingriffe ...
app.mount("/", StaticFiles(directory="static", html=True), name="static")   # zuletzt mounten
```

Das Beispiel sendet bewusst **kein `event:`-Feld**, und der Client unterscheidet nach `data.type`. Benannte Events landen nämlich nicht in `onmessage`, sondern nur bei passenden `addEventListener`-Aufrufen ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)). Ein neuer Event-Typ, den Person A hinzufügt, würde sonst im UI stillschweigend verschwinden. `StaticFiles` wird zuletzt gemountet, damit es `/api/...` nicht überdeckt. Zur Reihenfolge der IDs gilt: AUTOINCREMENT vergibt sie beim Insert. Hielte ein Schreiber eine lange Transaktion offen, könnte eine niedrigere ID nach einer schon gestreamten höheren committen und übersprungen werden. Mit kurzen Transaktionen und genau einem Schreiber zur Zeit tritt das praktisch nicht auf. Das ist ein weiterer Grund für die Regel „nichts Langsames in `tx()`“.

## Der Browser verzeiht viel, außer Fehlerstatus und zu viele Verbindungen

`EventSource` verbindet sich nach Netzwerkfehlern und nach normal beendeten Antworten automatisch neu und sendet dabei die letzte gesehene `id` als `Last-Event-ID`. Eine **Antwort mit einem Status ungleich 200 oder einem falschen Content-Type „fails the connection“, danach versucht der Client keinen Reconnect mehr** ([WHATWG HTML](https://html.spec.whatwg.org/multipage/server-sent-events.html)). Deshalb fängt der Generator oben Fehler selbst ab. Die zweite harte Grenze: Über HTTP/1.1 erlauben Browser **nur 6 Verbindungen pro Domain, über alle Tabs hinweg**. Chrome und Firefox haben das als „Won't fix“ markiert ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)). Plain uvicorn spricht HTTP/1.1. Also gibt es **genau eine EventSource pro Seite**, gefiltert wird im Client. Ein Stream pro Session-Zeile würde das Limit sofort sprengen.

Für das Laden der Seite ergibt sich ein robustes Muster. Zuerst kommt ein Snapshot per normalem JSON (`GET /api/sessions` und `GET /api/events?since=…`), dann wird die maximale ID gemerkt und `EventSource('/api/events/stream?since=' + maxId)` geöffnet. Der Client verwirft jedes Event mit `id <= maxId`. Das dedupliziert die Überlappung zwischen Historie und Stream sowie doppelte Events nach einem Reconnect. Ein Reload verliert so keinen Zustand, und SSE muss nur neue Events liefern. Der Retry-Wert wird in Millisekunden angegeben, nicht-ganzzahlige Werte werden ignoriert ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)). Falls die Demo hinter einem Proxy läuft: Nginx, Cloudflare und andere puffern standardmäßig ([sse-starlette](https://github.com/sysid/sse-starlette)), und die Spezifikation empfiehlt Kommentarzeilen „every 15 seconds or so“ für alte Proxies ([WHATWG HTML](https://html.spec.whatwg.org/multipage/server-sent-events.html)). FastAPI setzt Header und Pings bereits. Bei Nginx muss zusätzlich `proxy_read_timeout` über 15 Sekunden liegen.

Sicherheit ist hier kein Randthema. **Mail-Inhalte sind vom Absender kontrolliert.** Wer Betreffzeilen oder Mailtexte per `innerHTML` rendert, baut sich eine XSS-Lücke ins Operator-Dashboard. Konsequent `textContent` verwenden. Als Absicherung gegen eine Venue-Infrastruktur, die SSE puffert, dient Polling per `setInterval(() => fetch('/api/events?since=' + maxId), 1500)`. Es nutzt denselben Endpunkt, den man für die Historie ohnehin braucht. websocket.org empfiehlt Polling eigentlich erst ab Intervallen von 30 Sekunden ([websocket.org](https://websocket.org/tools/choose-a-protocol/)), aber das gilt für Produktionsmaßstab. Bei einer Handvoll Zuschauern ist ein billiger SQLite-Query alle 1,5 Sekunden vernachlässigbar. Das ist eine Abschätzung, keine Messung. WebSockets lohnen sich laut derselben Quelle für häufige bidirektionale Nachrichten. Für einen einseitigen Feed ist SSE einfacher, braucht keinen Upgrade-Handshake und verbindet sich selbst neu ([websocket.org](https://websocket.org/tools/choose-a-protocol/)). Die Eingriffe sind seltene, normale POSTs, eine WebSocket bringt also keinen Vorteil.

## Eingriffe brauchen eine atomare Sperre, keinen globalen Freigabe-Gate

Agent-Frameworks haben sich auf ein kleines Repertoire geeinigt. LangChains HITL-Middleware erlaubt, eine Aktion zu **genehmigen (`approve`), vorher zu ändern (`edit`) oder mit Feedback abzulehnen (`reject`)**. Dazu kommt `respond`, bei dem ein Mensch die Antwort liefert. Die Doku warnt ausdrücklich, `respond` nicht zum Ablehnen von Aktionen mit Seiteneffekten zu nutzen ([LangChain HITL](https://docs.langchain.com/oss/python/langchain/human-in-the-loop)). Das Gating wird **pro Aktionstyp und bedingt** konfiguriert, über eine `when`-Bedingung. LangChains Agent Inbox zeigt Thread-Status wie `idle`, `busy`, `error`, `interrupted` und `human_response_needed` und macht Threads über URL-Parameter verlinkbar ([Agent Inbox](https://docsearch.algolia.com/mcp/docs/repo/langchain-ai/agent-inbox)). Zendesk zeigt die Konsequenz einer Übergabe: Nach einer Eskalation **antwortet der AI-Agent auf dem Ticket nicht mehr** ([Zendesk](https://support.zendesk.com/hc/en-us/articles/8357756604186)). Microsofts HAX-Richtlinien fordern effizientes Aufrufen, Abweisen und Korrigieren (G7–G9) und **globale Steuerung (G17)**. Das ist die Grundlage für einen Not-Aus in der Kopfzeile ([Amershi et al., CHI 2019](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)).

Auf unseren Fall übertragen heißt das: **Pause/Fortsetzen pro Session, Übernehmen (manuelle Antwort, Agent schweigt), Entwurf freigeben/ändern/verwerfen, Zurückgeben an den Agent und ein globaler „Alle ausgehenden Mails stoppen“-Schalter.** Ein globales Approve-before-send wäre dagegen ein Eigentor. Jede Quote muss innerhalb von 6 Minuten raus, volle Zeitpunkte gibt es nur unter 2 Minuten. Nachts schaut niemand zu. Das passende Vorbild ist Intercoms „Ask for input“: Fin hält seine Antwort zurück und zeigt sie einem Teammitglied, und **wenn niemand reagiert, entscheidet der Timeout der Regel, ob Fin wartet, den Entwurf sendet oder übergibt** ([Intercom](https://www.intercom.com/help/en/articles/12396892-manage-fin-ai-agent-s-escalation-guidance-and-rules)). Für uns heißt das: Gates nur bei konkreten Bedingungen setzen. Sinnvoll sind niedrige Router-Konfidenz, fehlende RFQ-Felder (Gewicht, Maße, Flughafen), kein Tarif oder Bid gefunden, große Preisabweichung zwischen Quellen, ein Portalfehler oder eine Buchungsaktion. Dazu ein sichtbarer Countdown, und bei Ablauf geht der Entwurf automatisch raus. Smashing Magazine nennt eine gesunde Eskalationsrate von **5–15 % der Aufgaben** ([Smashing Magazine](https://smashingmagazine.com/2026/02/designing-agentic-ai-practical-ux-patterns/)). Liegt der Wert deutlich darüber, sind die Gates zu scharf und kosten Zeitpunkte.

Der technisch wichtigste Punkt fehlt in den Produktbeispielen, ergibt sich aber zwingend aus der Regel „nur die erste Quote zählt“. Das ist meine eigene Ableitung, keine zitierte Quelle. **Übernehmen muss in der Datenbank atomar gegen den Agent gewinnen.** Klickt der Operator auf „Übernehmen“, während der Agent gerade seine Quote abschickt, gehen zwei Quotes raus, und nur die erste zählt. Front löst das zwischen Menschen mit Kollisionserkennung und geteilten Entwürfen ([Front](https://help.front.com/en/articles/2403)). Bei uns sind die Kontrahenten Mensch und Agent, und die Lösung ist ein **bedingtes UPDATE als Claim**. Der Agent führt vor dem Versand in `tx()` aus: `UPDATE sessions SET control='sending' WHERE id=? AND control='auto'`. Nur wenn `rowcount == 1` ist, sendet er, außerhalb der Transaktion, und schreibt danach `quoted` plus Event. Der Takeover-Endpunkt macht dasselbe mit `WHERE control IN ('auto','paused')` und setzt `human`. Steht die Session schon auf `sending`, meldet das UI ehrlich „Agent sendet gerade“ statt eines scheinbaren Erfolgs. Der globale Not-Aus ist eine Zeile in einer `settings`-Tabelle, die der Versandpfad im selben Claim prüft. Weil `tx()` mit `BEGIN IMMEDIATE` startet, ist dieser Check-and-Set frei von Race Conditions.

Bei der Darstellung empfiehlt sich ein **Master-Detail-Layout**, wie es OpenAIs Agents-Dashboard und Temporal etabliert haben. Bei OpenAI ist jeder Eintrag eine Session, ein Trace zeigt Modellantworten und Tool-Calls, und pro Schritt sieht man Status, Dauer, Fehler und Token-Verbrauch ([OpenAI Agents Tracing](https://developers.openai.com/api/docs/guides/agents-api/tracing)). Temporal ergänzt einen Filter **„Pending and Failed Events Only“** und **pausierbare Live-Updates**, damit die Ansicht nicht springt, während jemand liest ([Temporal Changelog](https://temporal.io/changelog/updated-event-history-timeline-view-is-now-available)). Für unsere Seite heißt das konkret: In der Kopfzeile stehen KPIs (offene Sessions, Akzeptanzquote, Ø Antwortzeit, **Ø LLM-Kosten pro Quote gegen die 0,10-USD-Grenze**), ein Verbindungsindikator und der Not-Aus. Links steht die Session-Liste, **„Braucht Aufmerksamkeit“ oben angeheftet**, danach nach Deadline sortiert. Jede Zeile zeigt einen Countdown von 6:00 abwärts, gelb ab 2:00 (dort beginnen die Zeitpunkte zu fallen) und rot ab 1:00. Dazu kommen Filter-Chips und Volltextsuche über Kunde, Flughafen, Rate-ID und Betreff. Rechts folgen Zusammenfassung, Timeline mit Dauer und Kosten pro Schritt (`<details>` für Payloads), Entwurfsvorschau und Aktionsleiste. Deep Links wie `#s=<id>` bringen Alarm und Pitch-Demo direkt zur Session. Das erfüllt die Jury-Anforderung „Session finden und eingreifen muss einfach sein“.

Für Vertrauen sorgen Begründung und Ehrlichkeit, nicht grüne Häkchen. HAX G11 verlangt „Make clear why the system did what it did“, G16 die Folgen von Nutzeraktionen ([Amershi et al.](https://www.microsoft.com/en-us/research/wp-content/uploads/2019/01/Guidelines-for-Human-AI-Interaction-camera-ready.pdf)). Eine Studie zur Agentenaufsicht warnt, dass **„a reasonable process justifies overreliance“**. Bessere Zusammenfassungen fanden Fehler schneller, erzeugten aber mehr falsche Sicherheit. Die Studie empfiehlt, Annahmen explizit und editierbar zu machen und verglichene Alternativen sowie Quellen zu zeigen ([arXiv 2602.16844](https://arxiv.org/html/2602.16844v1)). Daraus wird die Karte **„Warum diese Quote“**. Sie zeigt den Kundenwunsch (günstigste/schnellste), die verglichenen Quellen (z. B. 3 Bids, 2 Sheet-Raten, 1 Portalrate), die gewählte Option mit All-in-Preis und Chargeable Weight, die preisrelevanten Annahmen und die zweitbeste Option mit Abstand in Prozent. Die Karte ist zugleich die beste Pitch-Folie für die 45 Genauigkeitspunkte. Ebenso ehrlich gehört Irreversibilität ins UI: „Quote gesendet, kann nicht zurückgezogen werden (erste Quote zählt)“ und „Rate-ID gültig bis 14:32“ mit Countdown, passend zur 15-minütigen Gültigkeit im Portal. Ein Undo-Button wäre hier eine Lüge. „Entwurf bearbeiten“ ist mehr wert.

## Fazit

Der eigentliche Erkenntnisgewinn ist, dass CRM, Live-Stream und Eingriffsmechanik keine drei Systeme sind, sondern **drei Lesarten derselben `events`-Tabelle plus einer `control`-Spalte**. Das CRM-Dashboard aggregiert die Events, der SSE-Endpunkt liest sie mit, und der Eingriff ist ein bedingtes UPDATE in derselben Datenbank, die auch den Agent steuert. Das reduziert das Risiko, das die Challenge am stärksten bestraft, nämlich stündliche, unangekündigte Setup-Änderungen. Jeder fehlgeschlagene Quote ist ein Event, das sofort im „Braucht Aufmerksamkeit“-Filter auftaucht. Und es macht die Codebase für die Jury lesbar, weil ein einziges Muster (`tx()` + `emit()`) überall wiederkehrt.

Offen bleibt einiges. Das Zusammenspiel von `threading.local` mit dem FastAPI-Threadpool unter echtem uvicorn-Betrieb ist aus Doku und Einzeltests abgeleitet, nicht unter Last gemessen. Das Verhalten von `uvicorn --reload` mit offenen Streams ist ungeprüft. Ob 1–2 Stunden für die Seite reichen, ist eine Einschätzung, keine Messung. Die Reihenfolge sollte deshalb lauten: zuerst das Event-Schema mit A und B festlegen, dann den JSON-Endpunkt `GET /api/events?since=` (der dient als Historie und als Polling-Fallback), dann SSE darüber. Den atomaren Claim im Versandpfad sollte das Team als Muss behandeln, nicht als Feinschliff, weil eine doppelte Quote nicht reparierbar ist.
